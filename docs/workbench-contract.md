# 工作台输入与要求

工作台是正式输入，包含内容、结构、状态、业务要求和来源。一次任务另行声明目标、处理范围与交付要求。工程检查清单作为已有模板保留，通用任务不要求 SWE 检查编号。

## 三层要求

| 层次 | 定义与检查 |
|---|---|
| 平台接入 | 格式版本、唯一编号、结构定义、对象关系、适用范围、来源可读性与输入大小 |
| 工作台业务 | `requirements` 至少一条；每条声明文字、适用对象、来源、优先级和验收方式 |
| 本次任务 | `task_type`、`goal`、`scope`、`deliverable`，以及可选补充 `requirements`；交付要求自动登记为 `task:delivery` |

接入校验允许未完成或不符合业务要求的记录进入：负责人缺失等问题正是任务要识别的对象。未声明结构、悬空引用、循环父子关系和重复编号会被拒绝。

## 格式

规范由 `/api/workbenches/contract` 返回，完整非工程示例见 [`fixtures/event-workbench.json`](../fixtures/event-workbench.json)。最小格式：

```json
{
  "format": "ai-workbench",
  "schema_version": 1,
  "id": "my-workbench",
  "title": "项目筹备",
  "revision": 0,
  "structure": [{"kind": "task", "label": "任务", "fields": {"owner": "负责人"}}],
  "objects": [{"id": "venue", "kind": "task", "title": "确认场地", "fields": {"owner": ""}, "source": "筹备记录"}],
  "requirements": [{"id": "owner", "text": "每个任务必须有负责人。", "object_ids": ["venue"], "source": "执行规范", "acceptance": "owner 字段有明确负责人。", "rule": {"kind": "required_fields", "fields": ["owner"]}}]
}
```

对象可以提供 `content`、`fields`、`state`、`parent_id` 和 `links`。`structure` 说明类型、字段含义及可选状态集合。对象编号与关系保持稳定，要求通过 `object_ids` 指向它们；空列表表示整个工作台。

要求可选字段规则：

- `required_fields`：所有适用对象的指定字段都有值。
- `field_equals`：指定字段等于声明的 JSON 值。
- `state_requires`：进入指定状态后，指定字段都有值。
- 未声明规则的要求交由助手判断，语义正确性仍需独立核对。

每条要求可使用 `conflicts_with` 引用同层的其他要求。服务还会识别同一适用对象字段被要求取不同值的冲突，包括工作台要求与任务要求之间的冲突。定性冲突仍需助手或人工识别。冲突保持在快照与结果中，用户解决要求后创建下一次任务。

## 导入

`POST /api/workbenches/import` 接收 `filename`、UTF-8 `content`，文件不超过 12 MiB。支持：

1. `ai-workbench` JSON。
2. 含 `<script type="application/json" id="workbench-data">` 的 HTML。
3. 本项目 `swe-handbook-record` JSON，知识版本必须匹配本机；不匹配时导入包含原知识的完整 HTML。
4. 原工作台 HTML 的 `record-data` 与 `bundle-data` 数据区块；保留记录、草稿、决策、影响与责任、附件元信息、文档以及对应检查要求。

导入读取 JSON 数据区块，不执行 HTML 脚本，不把任意应用页面推测成可写工作台。重复 JSON 字段或数据区块会被拒绝。规范化包上限为 800,000 字符、200 个对象、100 条工作台要求；单条内容为 16,000 字符，要求与任务目标为 4,000 字符。超限明确报错，不截断成看似完整的输入。

UTF-8 文本与 Markdown 附件会核对摘要并读取内容；其他附件标记为 `metadata_only`，导入提示和来源可读性会保留，不能作为“满足”结论的原内容证据。应用源代码、运行脚本与二进制资源不属于工作台业务快照。

原工程页面的“通用任务”按钮将当前已编辑记录送入新入口；完整工程知识从匹配版本的本机索引读取。导入失败或本机保存失败保留原文件与现有输入。

## 任务与结果

`POST /api/tasks` 接收 `TaskInput`，支持 `review`、`summarize`、`compare`、`organize`、`draft`、`plan`。空服务端范围表示全部对象；Web 要求显式选择至少一条，默认选择工作记录。

助手读取 `get_task_context`：所有要求、确定性检查、冲突、来源索引及总计最多 32,000 字符的原文摘录。摘录不完整时用 `read_task_source` 分页读取完整快照，每页不超过 8,000 字符。摘录限制不改变实际保存的原文。

最终 `TaskOutput` 包含：

- `requirement_results`：逐条覆盖工作台要求、补充要求与 `task:delivery`，编号以 `workbench:` / `task:` 区分。
- `verdict`：`met`、`unmet`、`unknown`、`conflict` 或 `not_applicable`。
- `artifacts`：至少一个与任务类型匹配的产物，并引用工作台资料。
- `changes`：整理、补写、计划可提供范围内的修改建议；评审、总结、对比输出产物。

每条要求结论必须引用对应要求。“满足”或“不满足”还需引用适用对象或用户回答，字段规则与已识别冲突的确定性结论不能被覆盖，范围内要求不能被跳过。原文引用与摘要由程序校验，引用的语义支持尚未独立评估。

最多一轮三个澄清问题，由用户在 Web 回答。最多三次结果提交，拒绝也计入；相同请求键的完全相同重试不再次执行。任务创建、问答、结果与修改应用都校验版本并保存回执。

## 修改与接续

修改只允许写入已声明对象的内容、状态或字段，禁止改变要求、结构或任意执行路径。`POST /api/tasks/{id}/apply` 接收任务版本、工作台摘要和用户选择的修改编号。冲突对象不能应用；应用前重新检查字段规则，拒绝破坏原先已满足的必须要求。成功后生成 `revision + 1` 的工作台包，原输入保持为不可覆盖的快照。

新版本是在本平台生成的包，未直接写入外部应用或原文件。下载工作台或选择“在此工作台上继续”，可以核对并开始下一次任务。Web 当前工作台已变化时，会阻止将旧结果直接应用到当前输入。

## 保存与能力边界

通用任务与原工程评审分别保存到数据目录，复用 SQLite 请求回执与 LangGraph 问答恢复。Web localStorage 保存输入、未确认请求、回答与最近打开的一份完整任务，重试前必须保存原请求。关闭标签页后仍可恢复；浏览器清除数据或写入失败不作恢复保证。

Android / iOS 提供浏览器入口，通用任务使用同一后端与响应式 Web 页面；原生离线库继续用于原工程评审。通用 Web 可离线阅读最近打开的任务及引用、生成报告和 JSON，新的任务与应用修改需要后端。

模型由连接的桌面助手触发，提交不会自动唤起助手。离线演示只运行声明的字段检查并生成固定示例产物，不代表模型完成语义任务。宿主调用次数、token、费用、独立语义质量均未测量。
